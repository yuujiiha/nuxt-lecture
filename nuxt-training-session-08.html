非同期UIとエラー処理
失敗を画面設計に含める

エラーを「例外」扱いせず、利用者が次に何をすればよいかまで設計する。

所要時間：約8〜10分1 / 10
Review & Goal

安全に失敗したら、分かりやすく伝える

前回

serverで守る

入力・権限・秘密情報・返却値を境界で管理した。

今回

UIで伝える

待機・失敗・空状態・復旧方法を画面に用意する。

ゴール

適切な範囲で処理

局所エラーとページ全体のエラーを使い分ける。

今日の問い：この失敗で、どこまで画面を止める必要があるか？

失敗は通常運転の一部2 / 10
Design Four States

非同期処理には4つの画面がある

PENDING

待機

何を待っているか。操作可能か。

ERROR

失敗

何が起きたか。再試行できるか。

EMPTY

空

0件は正常か。次の行動は何か。

SUCCESS

成功

取得結果を表示する。

チーム規約

非同期処理を追加したPRでは、成功時のスクリーンショットだけでなく、pending・error・emptyの挙動も確認する。

「データがない」と「取得に失敗した」を同じ表示にしない。

状態ごとに利用者の次の行動を考える3 / 10

AsyncData UI

statusとerrorを
UIへ反映する

const {
  data: users,
  status,
  error,
  refresh,
} = await useFetch('/api/users')

再取得の規約

再試行ボタンはrefresh中に無効化し、連打による重複実行を防ぐ。

<template>
  <LoadingState
    v-if="status === 'pending'"
  />
  <ErrorState
    v-else-if="error"
    :retrying="status === 'pending'"
    @retry="refresh"
  />
  <EmptyState
    v-else-if="!users?.length"
  />
  <UserList
    v-else
    :users="users"
  />
</template>
条件の順番も規約として揃える5 / 10
Page Errors

ページが成立しないなら
createError

対象例

  • URLの対象が存在しない
  • ページを表示する権限がない
  • 必須データを取得できない

詳細説明はmessage、短いHTTP表現はstatusTextへ置く。

const { data: user } = await useFetch(
  `/api/users/${route.params.id}`,
)

if (!user.value) {
  throw createError({
    status: 404,
    statusText: 'Not Found',
    message: 'ユーザーが見つかりません',
  })
}

// error.vueから復旧
await clearError({ redirect: '/users' })
404を空一覧として見せない6 / 10
Local Error Boundary

一部の失敗は
その場所だけ隔離する

NuxtErrorBoundary

default slot内のclient-side errorを受け止め、ページ全体ではなく該当領域だけ代替表示にできる。

例：おすすめ欄、グラフ、外部Widget。なくても主要機能が使える領域。

<NuxtErrorBoundary>
  <RecommendationPanel />

  <template #error="{ clearError }">
    <p>おすすめを表示できません</p>
    <button @click="clearError">
      再試行
    </button>
  </template>
</NuxtErrorBoundary>
主要機能を巻き込まない7 / 10
Action Errors

フォーム送信は「入力を失わせない」

送信中

送信ボタンを無効化し、進行中と分かる文言にする。

失敗

入力を維持し、修正箇所または再試行方法を示す。

成功

完了を伝え、一覧へ戻るなど次の導線を示す。

伝える内容

Takeaways

今日の3つの規約

非同期UIはpending・error・empty・successの4状態を設計する。

操作・component・pageの影響範囲に合わせてエラーを処理する。

エラー画面には、利用者が次に取れる行動を用意する。

次のPRでは、失敗ごとに「どこまで止まり、どう復旧するか」を確認する。
