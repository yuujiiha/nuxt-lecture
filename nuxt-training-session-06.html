Layouts

layoutsは
ページ共通の「枠」

向いているもの

  • Header・Sidebar・Footer
  • 管理画面と一般画面の枠の違い
  • ページ間で維持したい共通構造

個別ページの内容や業務ロジックはlayoutへ入れない。

// layouts/admin.vue
<template>
  <div class="admin-layout">
    <AdminSidebar />
    <main><slot /></main>
  </div>
</template>

// pages/admin/index.vue
definePageMeta({
  layout: 'admin',
})

Layout = 複数ページの外枠。Component = 画面内のUI部品。

共通だからlayout、ではなく「ページの枠」だからlayout6 / 10
Route Middleware

middlewareは
遷移前の判定

代表的な用途

  • ログイン必須ページの確認
  • 権限によるredirect
  • 不正な遷移条件の拒否

初回表示ではserverとclientの両方で動く場合がある。ブラウザ専用APIへ無条件に触れない。

// middleware/auth.ts
export default defineNuxtRouteMiddleware(
  (to) => {
    const user = useCurrentUser()

    if (!user.value) {
      return navigateTo({
        path: '/login',
        query: { redirect: to.fullPath },
      })
    }
  },
)

// page側
definePageMeta({ middleware: 'auth' })
重いデータ取得や画面描画はmiddlewareの責務にしない7 / 10
Do Not Confuse

名前が似ていても、実行場所が違う

場所

Route middlewareでしない

DBへ直接アクセス、秘密情報を読む、APIレスポンスを加工する。

Server middlewareでしない

画面コンポーネントを制御、Vue Routerのページ遷移を判断する。

「何の前に動くのか」を確認する：画面遷移か、HTTPリクエストか。

Takeaways

今日の3つの規約

URLはpagesのファイル構成で表現し、標準ルーティングを優先する。

ページ共通の外枠はlayouts、画面内の部品はcomponentsへ置く。

Route middlewareは、画面遷移前の認証・権限・redirectに限定する。

次のPRでは、遷移処理について「何の前に、どこで動くか」を確認する。
