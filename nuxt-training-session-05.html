ref / computed / watch

API
役割

URL Is State

画面条件はURLに置けないか考える

URLに向いている状態

  • 検索キーワード
  • ページ番号・並び順
  • フィルター条件
  • 選択中のタブ

URLならブックマーク・共有・戻る／進む・再読み込みが自然に動く。

const route = useRoute()

const page = computed(() =>
  Number(route.query.page ?? 1)
)

const setPage = (next: number) =>
  navigateTo({
    query: {
      ...route.query,
      page: next,
    },
  })
復元したい画面状態はURLを第一候補に5 / 10
useState

useStateは
SSR対応の共有状態

向いている場面

  • 複数componentで使う単純な状態
  • SSRからhydrationへ引き継ぐ状態
  • composable経由で共有したい値

値はpayloadへシリアライズされるため、関数・class・Symbolなどを入れない。

// composables/useCurrentUser.ts
export const useCurrentUser = () =>
  useState<User | null>(
    'current-user',
    () => null,
  )

禁止

// module直下のref
const user = ref(null)

サーバーではリクエスト間で状態を共有する危険がある。

keyは用途が分かる一意な名前にする6 / 10
When to Use Pinia

Piniaは「状態があるから」ではなく、複雑さに使う

GOOD FIT

GOOD FIT

GOOD FIT

Decision Guide

状態の置き場所を決める5問

そのUIだけ？ → refをcomponent／composable内に置く。

既存の値から計算できる？ → 新しい状態を作らずcomputed。

URLで共有・復元したい？ → params／query。

複数箇所で使う単純な状態？ → useState。

複雑な業務状態と操作？ → Piniaを検討。

同じ情報を複数の場所にコピーしない。Single Source of Truthを決める。

状態を増やす前に、導出できないか確認8 / 10

Takeaways

今日の3つの規約

状態は、必要とする範囲が最も小さい場所へ置く。

導出値はcomputed、副作用だけをwatchで扱う。

単純な共有はuseState、複雑な業務状態はPiniaを検討する。
