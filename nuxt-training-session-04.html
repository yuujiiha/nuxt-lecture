useFetch

APIから画面の
初期データを取得

チーム規約

  • ページのsetup直下で呼ぶ
  • URL・queryはリアクティブな値で渡す
  • dataだけでなくstatusとerrorも扱う
  • 必要なフィールドだけpayloadへ載せる
// pages/users/index.vue
const page = ref(1)

const {
  data: users,
  status,
  error,
  refresh,
} = await useFetch('/api/users', {
  query: { page },
  pick: ['items', 'total'],
})
useFetch = useAsyncData + $fetchの一般的な形5 / 10
useAsyncData

独自の非同期処理を
SSR対応にする

使うサイン

  • 外部SDKや独自clientを呼ぶ
  • 複数の取得をまとめる
  • 取得後に加工して返す
  • キャッシュを識別するkeyが必要

動的データでは、keyにもIDなどの識別子を含める。

const route = useRoute()
const id = route.params.id

const { data, status, error } =
  await useAsyncData(
    `user:${id}`,
    async () => {
      const [user, posts] =
        await Promise.all([
          api.users.get(id),
          api.posts.byUser(id),
        ])
      return { user, posts }
    },
  )
同じkeyはdata・status・errorを共有する6 / 10
$fetch

ユーザー操作の結果を
サーバーへ送る

代表的な場面

  • フォーム送信
  • 追加・更新・削除
  • 再試行ボタン
  • 明示的なユーザー操作

送信中は二重操作を防ぎ、失敗時はユーザーへ伝える。

const saving = ref(false)

const save = async () => {
  saving.value = true
  try {
    await $fetch('/api/users', {
      method: 'POST',
      body: form.value,
    })
    await navigateTo('/users')
  } finally {
    saving.value = false
  }
}
イベントハンドラー内でuseFetchを始めない7 / 10
Four UI States

通信処理は4状態をセットで設計する

PENDING

取得中

SkeletonやSpinner。必要なら操作を無効化。

ERROR

失敗

内容を伝え、再試行の導線を用意。

EMPTY

0件

不具合と誤解されない空状態を表示。

SUCCESS

成功

取得したデータを表示。

<LoadingState v-if="status === 'pending'" />
<ErrorState v-else-if="error" @retry="refresh" />
<EmptyState v-else-if="!users?.items.length" />
<UserList v-else :users="users.items" />
成功時だけ書いて終わらない8 / 10

Takeaways

今日の3つの規約

初期表示のAPI取得は、原則useFetchを使う。

独自の非同期処理はuseAsyncData、操作後の通信は$fetchを使う。

pending・error・empty・successの4状態を必ず設計する。
